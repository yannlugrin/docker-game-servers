## 1. Summary-back

A public GitHub repository publishes linux/amd64 Docker images to GHCR: one steamcmd **builder** image (Debian 13 slim, date-tagged, since steamcmd has no versions and self-updates), and one **runtime image per game**, built multi-stage with the game baked in at build time — never installed or updated at runtime — so tags honestly name the game version inside (`<version>-rN` immutable tags plus moving pointers). Every game image obeys a shared convention set: uid-agnostic and rootless, single documented state root, native config files as the authoritative interface with a small optional env-override surface, no secrets in layers or logs, stdout logging, an A2S-protocol healthcheck, bundled static Steam-query and RCON clients, and — the section the document treats as its heart — guaranteed clean shutdown on the stop signal, mediated by the entrypoint when the game ignores SIGTERM, with exit codes that never miscode a dirty stop as clean. CI provides on-demand builds, scheduled buildid-based update detection that auto-publishes new tags, and a smoke test gating every publish on the start/healthy/clean-stop path. The first game is Project Zomboid Build 42 (app 380870): Java server with its own JRE, `~/Zomboid` state root, game-rewritten INI config, two advertised UDP ports, optional RCON, no native SIGTERM handling (console `save`+`quit` mediation), a first-boot admin-password trap resolved by a fatal-or-create decision table, and native in-game backups as the preferred consistency mechanism.

## 2. Findings

**F1 — important — root §5.5 vs root §5.4: "unfiltered" stdout contradicts mandatory secret redaction.**
§5.5 requires "the game's output goes to stdout/stderr, **unfiltered**"; §5.4 requires "no secret may ever reach stdout... where startup logs echo configuration, credential values are redacted." When the game itself echoes its configuration to its console output — which Project Zomboid is known to do at startup with its server options — the two musts collide: redaction *is* filtering. An implementer must guess which must wins, and the two guesses produce observably different behavior (secrets in `docker logs` or not). Direction: qualify "unfiltered" in §5.5 (e.g., "unfiltered except the §5.4 redaction"), and have the PZ fact sheet state whether the server echoes password values at boot, since that decides whether the entrypoint may `exec` the game directly onto stdout or must interpose.

**F2 — important — root §7/§8/§5.8: the update-detection comparison is not implementable from the metadata the spec requires, and a buildid change without a version change falls between the tag categories.**
§8 says the scheduled job "compares each game's current Steam buildid against the newest published image" — but §5.8 requires labels to carry only "the game version and image revision", not the buildid, so the comparison's right-hand side is unspecified; two implementations would record it differently or infer it lossily from the version string. Worse, Steam depots routinely ship a new buildid with no change to the human-readable game version: §7 defines `-rN` bumps as "rebuild of the same game version (base refresh, entrypoint fix)" and new `<game-version>` tags as new game versions — a content change at an unchanged version string fits neither, and implementations will diverge on whether it triggers a build and what tag it gets. Direction: require the published image to carry the buildid it was built from (label), and state explicitly how a buildid-only change maps onto the tag scheme.

**F3 — important — PZ §2/§6, root §2.5: the claim that the main game port answers A2S is doubtful, and the port inventory may be incomplete.**
PZ §2 asserts one "main UDP game port (default 16261) which also answers the Steam query protocol." Historically the PZ server used dedicated Steam ports (`SteamPort1`/`SteamPort2`, defaults 8766/8767 UDP) for Steam networking/registration, and the fact sheet is silent on whether Build 42 retains any of them. If it does, the image cannot meet root §5.2's "documents every port" from this fact sheet, and the healthcheck target (PZ §6) and the `GAME_PORT` description ("game + Steam query") are built on the doubtful fact rather than merely recording it. The blanket "re-verify at implementation" mitigates but does not localize the risk: the assumption is baked into requirement-tier sections (§3, §6), not only the fact sheet. Root §2.5's general claim that servers answer A2S "on their game port" is also overstated as a universal fact — many titles use a separate query port. Direction: mark the query-port location and the existence/absence of dedicated Steam ports as explicitly-open verification items whose outcome feeds §3, §6 and the port table, rather than asserting the answer.

**F4 — important — PZ §4 (first-boot row Yes/Yes): a warning-only path contradicts the document's own "nobody reads warnings" doctrine for a credential divergence.**
When the database exists, `ADMIN_PASSWORD` is set, and the game offers no non-interactive password change, the prescribed outcome is "log a clear warning that the value was ignored." Root §5.4's stated reasoning for making missing secrets fatal is that "nobody reads warnings on a server that seems to work" — yet this row accepts exactly that mechanism for an operator whose rotated admin password silently did not take effect, a security-relevant divergence between believed and effective credentials. The row even names "silently diverging env and effective credentials" as the one forbidden outcome, then permits it in every practical sense. Direction: either make this case fatal by default (the operator unsets the variable to proceed, making the divergence impossible to miss) or attach reasoning for why a warning is sufficient here when it is insufficient everywhere else.

**F5 — minor — PZ spec: the state root's concrete location is left floating across sections that depend on it.**
PZ §2 gives "`~/Zomboid` by default; relocatable via the game's cache-dir option," and root §5.1 requires the image to document whether it honors `$HOME` — but the per-game spec never decides whether the image's documented state root is `$HOME/Zomboid` or a fixed path pinned via cache-dir. Under root §3.4's arbitrary-uid requirement (possibly no passwd entry, possibly no usable `$HOME` — where Java's `user.home` resolution is notoriously fragile), the two choices behave observably differently in what the operator must mount and what happens when `$HOME` is absent. The backup recipe (§8), smoke test (root §8) and README all hang off this path. Direction: have the PZ spec commit to one (or explicitly delegate with the validation requirement that an unusable `$HOME` is a loud fatal, not a `/Zomboid` or `?/Zomboid` surprise).

**F6 — minor — root §5.4 "should" vs PZ reality: env-injected secrets will persist into the backed-up state root, and the per-game spec does not address it.**
Root §5.4 says env-applied secrets "should not be persisted to a mounted path where the game permits working from an ephemeral copy." For PZ, the INI lives inside the state root, the game rewrites it, and no ephemeral-copy option is mentioned — so `SERVER_PASSWORD`/`RCON_PASSWORD` applied from the environment will land in the mounted, backed-up, game-rewritten INI. That may be unavoidable, but the per-game spec (root §6 requires it to document how each convention is honored) is silent on this convention. Direction: one sentence in the PZ spec stating whether an ephemeral config copy is possible and, if not, that env-injected secrets persist in the state root and backups.

**F7 — minor — both documents: decision identifiers (D-002…D-013) do not resolve within the specification.**
The reading contract promises reasoning attached to requirements "so it can be evaluated rather than merely obeyed", and the inline reasoning largely delivers that — but nine `D-nnn` citations point at a register that is not part of the two documents defined as the specification (it sits under `.claude/spec-work/`, working material an unsupervised implementer has no instruction to read). Direction: either fold the register into the spec (or reference its location normatively) or drop the IDs and let the inline reasoning stand alone.

**F8 — minor — root §7: the builder's date-tag scheme has no answer for a second same-day build.**
On-demand builds mint "a new date tag" (`YYYYMMDD`), and "a published immutable tag is never reused for different content" — so a second on-demand builder build on the same calendar day has no legal tag. Implementations will diverge (fail, silently skip, suffix). Direction: state the rule (refuse, or a same-day counter).

**F9 — minor — root §5.2: "The game must listen on 0.0.0.0" is a must addressed to the wrong party.**
The section opens by saying port configurability "is a property of the game, not of the image — an image cannot promise what the game does not offer," then issues a must about the game's bind address. The image can only default its configuration that way and document games that cannot. Direction: rephrase as an obligation on the image's shipped/effective configuration, with the honest-documentation fallback the rest of the section uses.
