## Cross-reference check

Every §N.M reference in both documents resolves. One nuance, not a finding: project-zomboid/SPECIFICATIONS.md:3 writes a bare "§6" for a root reference two lines before establishing that bare §N means this document; the surrounding words disambiguate it.

## 1. Summary-back

A public GitHub repo publishing Docker images for dedicated game servers to GHCR, in two tiers. One builder image carries steamcmd (pre-run at build time so its self-update is baked), can install any app id/branch with anonymous login, and is explicitly not a runtime image. Then one runtime image per game, each produced by a multi-stage build where the builder stage downloads the game and the final stage — Debian 13 slim, linux/amd64 only, because steamcmd is a 32-bit glibc binary — copies the game plus only its runtime deps, including the Steam client libraries the game dlopens. steamcmd is never in a game image; game content is baked at build time, never installed or updated at runtime, so a tag honestly names what is inside and consumers can pin by digest. Images are uid-agnostic (arbitrary --user, never root, nothing owned by a build-time uid) so operators isolate instances by uid over separate state dirs.

Each game image is mostly shared convention (§5) plus a small per-game delta captured in its own binding specification. The conventions are dominated by two silent failures the document keeps returning to: a stop signal that never reaches the game (hence PID 1 discipline, entrypoint-mediated save/quit, exit-code semantics, a 90 s grace-period floor, a CI smoke test that asserts exactly this path), and a secret leaking into a layer, a log, or a backup. Around those: native config files are the authoritative interface with a small optional env override surface, every port documented with an advertised-vs-remappable flag, stdout-only logging, a Steam-query HEALTHCHECK rather than a process check, a documented single state root, a consistent-backup recipe, and OCI labels carrying the Steam buildid. CI provides on-demand builds, scheduled buildid-based update detection with additive <version>-rN tags, and base-refresh rebuilds. The images orchestrate nothing, back up nothing, and name no hosting platform. First game: Project Zomboid B42 stable — Java, ships its own JRE, one game-managed state root pinned to a fixed path independent of $HOME, config files the game rewrites, admin credentials in a DB that prompts interactively on a fresh install (the dangerous first-boot branch), no native SIGTERM handling, native backup settings, workshop mods downloaded by the game at startup.

## 2. Findings

**F1 — blocking — root §5.6 (table row 2), PZ §5, root §8.** The document calls §5.6 its strictest section, yet the one number that decides whether the mediated shutdown prevents or causes a truncated save is absent. The requirement is "Bounded wait, then terminate the game process; exit non-zero" — bounded by what, relative to the operator's runtime grace period the image cannot read? Two reasonable implementations diverge in exactly the corruption dimension: a short internal bound (say 30 s) terminates a PZ server mid-save on a large map, which is the failure §5.6 exists to prevent; a long internal bound (say 300 s) means the runtime's SIGKILL always lands first, so the non-zero "save unconfirmed" exit code of the exit-code contract never reaches the supervisor. Compounding it, "confirmed clean stop" (PZ §5: "exits 0 only on a confirmed clean stop") is never defined — one implementer will treat the game process exiting 0 after quit as confirmation, another will require evidence the save flushed (which PZ §8 itself lists as unverified), and only the first will ever pass the §8 smoke test's "exit 0". Direction: state the observable contract — how the internal wait relates to the operator-configured grace period (including that it be operator-visible/adjustable and documented alongside the 90 s recommendation), and what evidence counts as a confirmed save for exit 0 versus non-zero.

**F2 — blocking — root §7, §8, §5.8, §6 (fact list); PZ §2.** The tag namespace is the project's main consumer-facing contract and rests on a <game-version> string whose origin is never specified. §5.8 states the version string "cannot be compared against Steam's metadata reliably" and that buildids change without version changes; §8's scheduled job detects a buildid change but is then required to act "on a new game version" and publish "the new tags" — deciding between a new <game-version>-r0 and a revision bump of the existing version requires reading the human version string from somewhere the document never names, and §6's minimum per-game fact list does not include it (PZ §2 mentions "version 42.20" as prose, not as a machine-readable source). Two further observable behaviors hang off the same gap: how "newest game version" is ordered for the moving latest pointer (string sort makes 42.9 newer than 42.10), and what an on-demand rebuild of an already-published version+buildid does — publish r+1 or refuse. Direction: add the version-string source to §6's required facts (and to PZ §2), state the ordering rule for latest, and say whether an identical-buildid rebuild is a legitimate revision bump.

**F3 — important — root §5.3 vs PZ §4 (with root §6).** Root §5.3 states as a must: "The image must be fully operable with a mounted configuration and not a single game-specific environment variable set." PZ §4 makes ADMIN_PASSWORD fatal-if-missing on a fresh state directory, and the PZ admin credential lives in the server database, not in the mounted INI — so on first boot the PZ image is not operable without a game-specific variable. Since §6 says a per-game document "never weakens a must", these cannot both stand. §5.3 also contradicts itself in place: it forbids requiring variables in one sentence and defines "mandatory" variables two bullets later. The risk of leaving it: an implementer trying to satisfy the root must invents a seeding path (a password file, a generated random password) and the loud first-boot failure PZ deliberately designed is lost. Direction: qualify the §5.3 must to exempt mandatory secrets per §5.4 that the game accepts by no other route, or state explicitly that first boot may require one variable.

**F4 — important — root §5.5, §2.5; PZ §6, §2.** The healthcheck requirement asks the probe to report something the probe cannot see, and stakes the container's liveness on an operator-configurable game feature. "[The check] must fail once the server no longer accepts players" is not derivable from an A2S reply: a server at max players still answers normally, and an implementer reading this literally will mark a full server unhealthy — which, under any orchestrator with restart-on-unhealthy, turns a popular server into a restart loop. Separately, §5.5 makes the Steam-query probe mandatory for every game image while neither document states what happens when the game is configured to run without Steam integration (PZ's fact list is silent on whether B42 offers this); in that configuration the container is permanently unhealthy for a healthy server. Direction: restate what the probe must actually distinguish (answers queries vs. does not, after load), and either add "can this game run with Steam integration disabled" to §6's fact list with a documented consequence, or state that a Steam-disabled configuration is unsupported.

**F5 — important — root §7, §11, §5.7; PZ §8.** A whole class of irreversible data loss is unaddressed: pulling a new image can migrate an existing world to a new game version with no way back. §11's "No runtime game updates" blast radius is given purely as "servers lag behind releases by one rebuild", and §7 offers moving <game-version> and latest tags that will carry an operator across game versions automatically on the next pull. Nothing requires the documentation to warn that a new game version may migrate or break saves, or to tell the operator to back up before moving tags — even though §5.7 exists precisely to own backup knowledge and PZ §2 notes the game has a "backup on version change" setting. This is the same shape as the failures the document does treat: silent, discovered late, unrecoverable. Direction: add a save-compatibility/upgrade warning obligation to §5.7 or §9 (and to §6's minimum coverage), and mention the risk in §7's moving-tag caveat.

**F6 — important (misclassified tier) — root §8, third bullet.** "Game images should also be rebuilt (revision bump) when the base or the builder image materially changes — security patches reach game images no other way once games are baked in. A scheduled base refresh should exist for the same reason." The clause carries its own must-grade reasoning: given §3.2's baking decision, this is the only CVE-remediation path for multi-gigabyte images that will otherwise sit unpatched indefinitely. As a "should", the most laborious CI piece is the one an unsupervised implementer may legitimately drop, and the document's own tier contract says deviation from a should only needs a reason. Direction: promote both to musts, or state honestly which part is optional and what the operator is expected to do instead.

**F7 — important — PZ §4, §3.** The first-boot decision table keys on "Server database exists", unqualified. PZ configuration and save sets are per-server-name (SERVER_NAME "selects the config/save set under the state root"), so the database is per server name too — and an implementer who tests "any database present in the state root" produces exactly the failure the table exists to prevent: an operator who changes SERVER_NAME on an existing state root falls into the No-DB/No-password case, but is evaluated as Yes-DB, and the game hangs on the interactive prompt. Direction: state that the existence test is evaluated against the effective SERVER_NAME's database, and say what happens when SERVER_NAME changes on a populated state root.

**F8 — important — root §5.1, §3.4, §2.7; PZ §1.** The writable-path surface of the PZ image is left ambiguous in a way that decides how many mounts operators need and whether --read-only works at all. Root §5.1 requires the image to "honor $HOME when the game derives paths from it, and … document whether it does"; PZ §1 deliberately pins the state root away from $HOME because a no-passwd-entry uid has no usable home — but then never says whether $HOME is set to anything writable, or whether anything else needs to write outside the state root and /tmp. Root §2.7 warns in detail that the Steam client libraries are typically resolved via ~/.steam, and PZ §2 leaves it open whether the server uses that link farm; a link farm the game expects to write into (or a JVM/Steam crash-dump path under an unwritable home) is the classic first-build failure the document elsewhere works hard to preempt. Direction: require the per-game document to enumerate the complete writable-path set (state root, /tmp, $HOME or its absence) and to state whether the image sets $HOME itself, so the read-only-rootfs "should" is checkable.

**F9 — minor — root §5.5; PZ §3, §6.** Two healthcheck details left to guess where implementations visibly diverge: (a) the probe must follow the effective port when GAME_PORT is overridden — a baked-in default port makes a correctly-running server permanently unhealthy; (b) start_period "must absorb worst-case load time", but the worst case is first-boot world generation, and sizing for it blinds hang detection on every subsequent restart for the same duration. Direction: say the probe targets the effective configuration, and acknowledge the start-period trade-off so the choice is deliberate and documented.

**F10 — minor (tier hygiene) — root §2.1, §2.6.** §2 is introduced as "facts about tools, protocols and products. Not decisions" — but §2.1 ends with a decision ("Debian 13 slim … the project's chosen base for every stage") and §2.6 is a decision throughout (GHCR, with its justification). Both are re-stated as requirements later (§4.2, §7), so nothing breaks; but mixing closed decisions into the facts tier undermines the reader's ability to tell what may be re-evaluated against evidence from what may not. Direction: keep the fact (musl/32-bit rules out Alpine; slim Debian is the floor) in §2 and move the base and registry choices to §3/§7 as reasoned musts.

**F11 — minor (tier ambiguity) — root §5.5, §5.1, §6.** "Game images ship two minimal static clients" reads as a must but ends "images whose game needs neither may drop them with reason" — a should-style escape inside a must, which §6's "never weakens a must" then cannot classify. Two nearby load-bearing shoulds deserve a second look for the same reason: the single state root (§5.1) is treated as given by §5.7's backup recipe, and the read-only-rootfs run is the only stated verification that no state hides in undeclared locations. Direction: pick a tier for each, or restate the clients requirement as a should with the two capabilities as musts.

**F12 — minor — root §3.4, §8.** The image's default user is unstated, and it is operator-visible: an image defaulting to root creates root-owned files in the operator's volume on first run, so a later --user 1000 hits PZ §1's fatal unwritable-state-root path; an image defaulting to a non-root uid does not. Relatedly, §8's smoke test asserts the §5.6 path but nothing asserts §3.4 — the uid-agnostic promise, the project's stated reason for the whole ownership rule, is never exercised in CI. Direction: state the default-user behavior (or that the image must behave identically either way), and consider extending the smoke test to run under an arbitrary uid with a read-only rootfs.

**F13 — minor — root document as a whole; §4.3.** The root document admits no blind spots of its own. The PZ document does this well (dated facts, an explicit "open port facts, to settle" list, "to verify at implementation" markers), but the root asserts its environment facts flatly — that trixie-slim is the smallest mainstream option, that the two shipped clients "add megabytes, not tens of megabytes" — with no marker of what would change if they turn out wrong. One asserted mechanism I would also flag: §4.3 requires credentials "acceptable via the environment at build time without ever being written to a layer", and a plain build-time environment/ARG is precisely what does persist in image history — the requirement and the named channel sit in tension. Direction: add a short uncertainty note to the root (or mark the size claims as "measured at implementation"), and restate §4.3 in terms of the guarantee (never persisted in any layer or in build history) rather than the channel.

**F14 — minor — PZ §8, §2; root §5.5.** PZ relies on the game's native backup feature as the preferred consistent path, with archives landing inside the state root, and the operator told to "cap their count to bound disk growth" — but nothing states what the image's shipped or effective configuration does with those settings by default. Root §5.5 warns that a slowly-filling state disk corrupts saves; a default of backup-on-every-start with no cap is that failure, and a default of off silently removes the preferred backup path the docs recommend. Direction: state the intended default for the native backup settings and the cap, or state explicitly that the image leaves them at the game's defaults and documents what those are.

## 3. Questions for the operator

1. Where does the <game-version> string come from for a tag — the installed game's own files, a manual CI input, or Steam metadata — and is a rebuild at an unchanged version and buildid a legitimate r+1? (F2)
2. What should the entrypoint's shutdown wait be, relative to the operator's grace period, and should it be operator-adjustable? (F1)
3. What counts as a "confirmed" clean save for exit 0 — the game process exiting 0 after quit, or positive evidence the save flushed? (F1)
4. Is a first-boot-mandatory ADMIN_PASSWORD an accepted exception to §5.3's zero-env-vars must, or should the image accept the admin credential by some other non-interactive route? (F3)
5. Can the PZ B42 server run with Steam integration disabled, and if so, is that configuration supported by this image (healthcheck implications)? (F4)
6. Should the documentation own a save-compatibility/upgrade warning across game versions, or is that deliberately the operator's problem? (F5)
7. Are the base/builder-refresh rebuilds of §8 genuinely optional, and if so what is the intended patching story for baked images? (F6)
8. Does the PZ image set $HOME, and what is its complete writable-path set beyond the state root and /tmp? (F8)
9. What is the image's default user, and should CI verify the uid-agnostic and read-only-rootfs promises? (F12)
10. Are the native backup settings left at game defaults, or does the image impose a bounded default? (F14)

2 blocking, 6 important (plus 6 minor) — not a quiet round; the shutdown bound (F1) and the version-string/tagging gap (F2) both sit on paths the document declares central and would each force an unsupervised implementer to guess in a direction the document cannot audit.
