# Review — handoff prompt (`.claude/spec-work/handoff/PROMPT.md`)

## 1. Summary-back — the implementer's first session, step by step

A fresh session at the repository root is told to read this prompt in full and do what it says. It reads the three specification documents (root, `steamcmd/`, `project-zomboid/`), learns that the repository is a monorepo with three tracks (root, `steamcmd`, `project-zomboid`), and absorbs eleven permanent ground rules: specs are read-only with an operator-gated amendment channel (with a carved-out autonomous path for the 15 pre-committed PZ open facts plus root §2.9); one gated step at a time with self-verification before handover; all memory in files (per-track `PLAN.md`/`DECISIONS.md`, one repository-wide `CLAUDE.md`, `.claude/docs/` for lazily-loaded notes, `.claude/refs/` as read-only operator input); decisions logged; no secrets; small step-prefixed commits with annotated `step-*` tags; English; a descriptive `README.md`; an action boundary separating the free local development loop from gated registry/GitHub/destructive actions; a persistence budget; and a proportionality rule.

It then produces eight files without writing any project code: three plans, three decision logs, `CLAUDE.md` and `README.md`. The plans must cover every section of every spec document, order work by dependency (steamcmd builder before the PZ image, conventions inside the game image, CI after build definitions, docs alongside each deliverable), put cheap steps first, and open with three gated root-track foundation steps — `step-000` the harness (`.gitignore`, pinned deps + setup command, a `just`-driven check/test/verify built on `pre-commit`, wired into hooks and a CI workflow, prose lint over the governance documents), `step-001` the permission/hook baseline in `.claude/settings.json` plus live probes of what actually enforces anything, `step-002` the workflow tooling instantiated from `.claude/spec-work/handoff/assets/`. Plans must flag external prerequisites (GitHub repo/remote and first-push authorization, the GHCR owner namespace, per-package public-visibility flips, a conditional Docker Hub credential) and end with an open-questions section.

Finally it commits the eight files as one `meta:` commit, spawns a fresh read-only subagent with an inline prompt to cold-review the plans against the specs (coverage, ordering, granularity, proportion, prerequisites, consistency, premises), triages the findings, and presents plans plus triage for approval. `step-000` starts only after the operator approves.

## 2. Findings

### 1 — important — rule 2 ("check ... untracked files included") vs the mandated `pre-commit` runner
Rule 2 defines *check* as "syntax, lint and formatting over the whole working tree, **untracked files included** and gitignored paths excluded", and in the same paragraph fixes the mechanism: "the `pre-commit` framework as the hook runner". `pre-commit run --all-files` enumerates files through `git ls-files` — i.e. **tracked files only**. An untracked new file is exactly what a step lands, so the two mandates collide in the one place where the failure is silent: `just check` reports green having never run a hook on the file the step added. Either the implementer notices and writes glue (`git add --intent-to-add` before the run, or an explicit file list), or it does not notice and the harness quietly under-covers from step `000` onward. Suggested direction: state the observable ("a lint error in a file not yet added to the index must fail `check`") and acknowledge that satisfying it with `pre-commit` needs an index-priming step, or drop the untracked requirement and rely on the commit hook for that case.

### 2 — important — `step-000` ships a deliverable its own gate cannot test
`step-000` bundles: `.gitignore`, pinned dependencies plus a setup command, the whole check/test/verify harness, wiring into commit hooks **and** a CI workflow (with toolchain caching and a periodic uncached run), and a prose-lint configuration tuned to ~1500 lines of read-only specification prose it may not modify ("the lint bends to them and never the reverse", each exclusion a logged decision). Its stated test is "a fresh clone, the setup command, the check command, one commit — all green" — which exercises none of the CI workflow, and the prompt concedes as much: "treat the workflow as verified only once I authorise the first push". That contradicts the plan-ordering rule two paragraphs earlier ("everything on GitHub ... is shared public state and comes last") and produces an approved, tagged step containing an untested artifact — the state every later session treats as known-good. The prompt does invite splitting ("If one of the three is still too big for a single test ... say so"), but it also *specifies* the CI workflow as part of `step-000`, so the invitation and the instruction pull opposite ways. Suggested direction: keep `step-000` to the local harness (hooks + `just` entry points + lint config) and make the CI workflow its own root-track step sequenced at the first-push authorization, which is already a listed prerequisite.

### 3 — important — rule 9's free side does not cover bootstrapping the toolchain, which is `step-000`'s entire job
Rule 9: "anything local and read-only you run freely ... **installing the repository's pinned dependencies through the documented setup command** included; **fetching anything not pinned in the repository is not local**." At `step-000` neither the pinned dependency set nor the setup command exists yet — the step creates them. Installing `pre-commit`, `just`, a Dockerfile linter, a shell linter and a prose linter to discover and pin their versions is therefore "not local", while it is also absent from rule 9's enumerated gated side (registry writes, `git push`, GitHub writes, outward side effects, unscoped Docker sweeps, history rewrites). Two reasonable implementers diverge visibly: one asks the operator before each install, the other proceeds. The same hole shows up later — `apt-get` inside a local image build fetches unpinned content, yet "building this project's images locally" is explicitly free. Suggested direction: say plainly that acquiring the repository's own toolchain and the content a local build pulls (apt, base images, Steam) is on the free side, and reserve the "not pinned" clause for fetching material into the repository as a dependency.

### 4 — important — the enforcement probes are pinned to `step-001`, but two of the mechanisms only exist at `step-002` or later
Rule 2: "prove once, **at step `001`**, what each enforcement mechanism actually does in your version, one probe per mechanism — they are independent, and one passing says nothing about the other." At `step-001` there are no skills, no agents and no `.claude/rules/` file; those arrive at `step-002` and beyond. Rule 3 separately says the rules-file mechanism is probed "before relying on that mechanism", which is a different time. More concretely: every reviewer template declares its read-only discipline through agent frontmatter `tools:` (`step-reviewer`: `tools: Read, Glob, Grep, Bash`; `state-reviewer`, `code-reviewer`, `test-reviewer` add `Write`), and that mechanism is nowhere in the probe set — while the prompt has already established that the *skill* analogue (`allowed-tools`) "restricts nothing at all". So the templates rest a safety property on an unprobed guard, in a prompt whose own stake is "an unenforced allowlist is a guard that exists only on paper, and the failure announces nothing". Suggested direction: attach each probe to the step that introduces its mechanism (settings keys and permission patterns at `001`; agent `tools:` and `.claude/rules/` at `002`, reported the same way), rather than fixing them all at `001`.

### 5 — minor — the shipped clients are described as replaceable "should"-tier, but the PZ document already settles them
Rule 2 lists "root §5.5's Steam-query and RCON clients, project-zomboid §4's SQLite client — 'should'-tier defaults you may replace with a logged reason". Root §5.5 is indeed a recommended default, and PZ §4's SQLite client is conditional ("if the entrypoint needs one"). But PZ §6 states flatly: "**Both static clients of root §5.5 ship**: the query client drives the healthcheck and serves operators; the RCON client is useful to operators only when operator RCON is enabled" — the per-game document has already exercised the latitude and adopted them, and root §6 says a per-game document "may deviate from a 'should' with reason, but never weakens a 'must'". An implementer following the prompt could log a decision dropping the RCON client and land in conflict with PZ §6. Suggested direction: scope the "you may replace" latitude to the root-level default and note that PZ §6 has already settled it for this image.

### 6 — minor — the mandatory-escalation list of open facts omits (f), whose unfavorable path is the same class of change as (d)
Rule 1 always requires a return to the operator for unfavorable resolutions of PZ items "(d), (e), (g), (k) or (l)", glossed as "those change the offered environment surface, the tag naming, the read-only claim, ship a documented-degraded profile, or block shipping". Item (f)'s pre-committed unfavorable path is "a documented image-behavior variable selects the probe mode" — that is a new operator-facing environment variable, i.e. exactly "the offered environment surface" that earns (d) its place on the list, and it is not obviously caught by the general clause ("a requirement, a tier, a documented limitation or the decision to ship"). As written, one env-surface addition is autonomous and the other is not. Suggested direction: add (f), or restate the general clause as "any change to the documented operator surface" so the enumeration becomes illustrative rather than load-bearing.

### 7 — minor — `step-000` mandates a periodic uncached CI run before there is anything to build
"cache the toolchain, but keep a periodic uncached run proving a fresh setup still works" creates a second scheduled workflow at the foundation step, for a repository that at that point contains only lint configuration — against rule 11's own "Build at the moment of need, not in anticipation of it". It also inherits root §2.8 (GitHub disables `schedule` workflows after ~60 days idle), which the prompt does not mention here even though root §8's refresh is required to be deactivation-resistant for that reason. Suggested direction: drop it from `step-000` and let the fresh-setup proof ride the refresh workflow root §8 already requires, or state it as a "should" the implementer may defer.

### 8 — minor — the external-prerequisite list omits repository visibility and Actions enablement
The list covers the repository and remote, first-push authorization, the GHCR owner namespace, per-package visibility flips, and a conditional Docker Hub credential. Root §1 requires a **public** repository, and root §2.8's schedule-deactivation fact is specifically a public-repository behavior, while root §2.6's free public GHCR hosting assumes it — making the repository public (and having Actions enabled on it) is an operator-only action that no listed prerequisite names. Suggested direction: fold "the repository exists, is public, and has Actions enabled" into the first prerequisite line.

### 9 — minor — three governance file pairs for a track whose specification adds no requirements
The prompt requires `steamcmd/PLAN.md` and `steamcmd/DECISIONS.md` as a full track, but `steamcmd/SPECIFICATIONS.md` says "This file adds no requirements of its own; it exists so every image directory carries the same layout" — the track's whole content is root §4 (four short paragraphs) plus §8's builder gate. The cost is not the two thin files but the consequence they force on every ritual: because the governance placeholders "never resolve to one literal path here", each instantiated skill must carry track-resolution logic at invocation. Two tracks (root owning the builder, `project-zomboid` owning the game) would remove that for a plausibly small loss. Suggested direction: either state why the builder needs its own track and step namespace, or collapse it into the root track and let `project-zomboid` be the only component track.

### 10 — minor — the milestone-close tooling has no trigger if the plans have no milestones
Rule 3 makes memory compaction "mandatory whoever performs it" at a milestone close, and `step-002` instantiates `state-reviewer`/`optimize-memory` because "a milestone close needs its state review and its memory compaction to exist before it arrives". But milestones are optional throughout ("grouped under milestones **when the plan is big enough that grouping helps**"), and the `approve-step` template's only trigger for both passes is "if this was the milestone's last step". If the implementer's plans carry no milestones, the certainty test that justifies up-front instantiation fails, and the fallback trigger ("whenever the memory files have grown noticeably") lives only in `CLAUDE.md` prose with no ritual that fires it. Suggested direction: either require milestone grouping in these plans, or give the compaction pass a milestone-independent trigger the ritual can check (for example, every Nth approved step, or a line-count threshold in `approve-step`).
