## 2. Findings

**F1 — important — PROMPT rule 3 / first-task step-000 bullet vs `assets/approve-step.md` (header + step 4): the milestone-ritual fallback dangles once a template is dropped.**
Evidence: the prompt rules that "an instantiated file must never name a skill or agent you did not adopt: trim the reference or adopt it", with one carve-out — "a name that sits on `CLAUDE.md`'s not-yet-adopted list is not dangling". The approve-step template header orders the opposite preservation: "keep the step even when they [`state-reviewer`, `optimize-memory`] are not adopted — it falls back to `CLAUDE.md`'s not-yet-adopted list, and deleting it removes the passes' only in-ritual trigger." But the list only holds *not-yet-adopted* templates: an explicitly **dropped** template leaves the list (and once every template is adopted or dropped, the whole block and directory are deleted per rule 3). At that point approve-step step 4 names agents that are neither adopted nor listed — exactly the dangling name the prompt forbids — while its header forbids trimming the step. Rule 3 does define the real fallback (a fresh subagent briefed inline), but no text tells the instantiator to rewire step 4 to it; two reasonable implementers diverge (keep dangling names citing the header, or trim step 4 citing the prompt and lose the compaction pass's only in-ritual trigger — a silent skip of a mandatory pass). Direction: one sentence, in the prompt's instantiation paragraph or the template header, stating that when those agents are dropped (or the assets block deleted), step 4's fallback becomes rule 3's inline-subagent briefing as restated in `CLAUDE.md`.

**F2 — minor — the adaptation instruction understates what the templates assume (PROMPT rule 3 "Starter templates" paragraph vs `orient.md`, `step-reviewer.md`, `state-reviewer.md`, `optimize-memory.md`).**
Evidence: the prompt says to "adjust their `PLAN.md`/`DECISIONS.md` references to resolve the active track's files, since the templates assume a single plan". The templates assume more than a single plan: a single `SPECIFICATIONS.md` (step-reviewer step 3 "Read those spec sections in `SPECIFICATIONS.md`"; state-reviewer's frame — plan steps will cite sections across two documents); a single `D-NNN` namespace (optimize-memory's dangling-reference grep cannot validate per-log ids, which rule 4 says are cited as file-plus-id across logs); and orient's enumerated routine ("PLAN.md's current step", "the tail of DECISIONS.md", "spec sections the step lists") is narrower than rule 3's session-start routine it claims to execute (root plan and log plus active track's plan, log and full `SPECIFICATIONS.md`). Instantiated literally versus adapted per rule 3, the resulting rituals differ observably. Direction: broaden the adaptation sentence to cover spec-document references, the per-log decision-id namespace, and state that rule 3's routine wins over a template's enumeration on conflict.

**F3 — minor — `.claude/settings.json` sits outside every standing check family (PROMPT rule 2).**
Evidence: rule 2 adds `.claude/skills/` and `.claude/agents/` well-formedness to the harness on the reasoning "a malformed skill does not fail, it silently never loads", and orders a **one-time** step-000 probe that the settings baseline binds. The file carrying that baseline — the enforcement mechanism itself — appears in no check family, so an edit after step 000 that malforms it fails exactly as silently as a malformed skill, with the probe long past. Direction: either include settings well-formedness in the standing check list or make the binding probe a standing harness check rather than a step-000 one-off.

Beyond these: the check families match the stack (Dockerfiles, shell entrypoints, Actions/compose YAML, markdown); the rule-9 action boundary covers every paid/destructive/shared-state action the spec implies (image publish, git push, any GitHub/GHCR write including visibility and deletion, state-destroying local git), with the free carve-outs (local builds, anonymous reads) spec-consistent; the external-prerequisites list (visibility flip per §2.6/§8, first-push authorization, conditional Docker Hub credential, no Steam credential) is complete and spec-supported; every file a cold-started implementer is told to read exists on `main`; the pre-first-tag case of the re-orientation command is handled; the cold-review instructions keep the reviewer out of `.claude/spec-work/` and are self-sufficient (the workflow rules it audits against live in the just-written `CLAUDE.md`); no instruction sends any session into `.claude/spec-work/` beyond the prompt and its assets.
