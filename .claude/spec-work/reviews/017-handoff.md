## 2. Findings

**1. Minor — Rule 3 / first-task item 3 vs. step-000.** `CLAUDE.md`, written at bootstrap, carries the standing instruction that an interrupted session "runs `/resume-step` before touching anything" — but the skill is instantiated only in step-000. In the window between the `meta:` commit and step-000's tooling commit (which includes an interruption *during* step-000, the likeliest early interruption: settings probes, harness bring-up), a resuming session is directed at a command that does not exist. The failure is loud (unknown command), but the fallback is unstated; the not-yet-adopted-list carve-out is framed only for the milestone ritual. Direction: have the prompt state the pre-instantiation fallback (follow the template's doctrine manually from the session routine, or name the carve-out as covering this reference too).

**2. Minor — first-task step-000 vs. rule 2's granularity doctrine.** Rule 2 says "Never batch several steps because they look small" and the plan instructions require "Steps must be small enough that I can test each one alone" — yet the prompt itself fixes step-000 as one step bundling `.gitignore`, pinned setup, the full check/test/verify harness, pre-commit hooks, a CI workflow, governance lint, the settings baseline plus guard hook, three enforcement probes, and five tooling instantiations. The single stated test (fresh clone / setup / check / one commit) does not exercise several of these deliverables (the probes, the tooling, the CI workflow — which the prompt itself declares unverifiable until first push). The cold reviewer is instructed to audit granularity and would find its first violation in the prompt-mandated step. Direction: either bless step-000's breadth explicitly as a deliberate exception with its composite test, or permit splitting the foundation into a few gated steps.

**3. Minor — external-prerequisites bullet cites root §2.6 for something it does not say.** The prompt: "the repository itself is already public, which root §2.6's free hosting and root §2.8's schedule behavior both rest on." Root §2.8 does rest on repository visibility; root §2.6's free hosting rests on *package* visibility (the per-package flip), not on the repository being public. The underlying fact is true (verified), so only the citation over-reads. Direction: drop the §2.6 half or reword to "public packages".

**4. Minor — rule 2 hardens a spec "should" into a stack fact.** "the two static clients of root §5.5, which enter the repository pinned … and are covered like any other shipped artifact": root §5.5 makes the two clients a *recommended default* ("a game needing a different mechanism documents what replaces them"), and the spec nowhere requires them to enter the repository; PZ §4 also adds a possible third shipped tool (the SQLite client) in the same class, which the sentence omits. The "expected instance, not the boundary" framing mostly absorbs this, but the flat wording could make an implementer treat the two clients as settled rather than a logged-deviation candidate. Direction: phrase it conditionally ("where the §5.5 clients are adopted, they enter pinned…") and say "shipped static tools" rather than enumerating two.

**5. Minor — the ask-tier enumeration for local git omits history rewriting.** Step-000's baseline asks for "state-destroying local git (`reset --hard`, deleting tags or branches)" on the reasoning that step tags and the working tree are the memory rules 3 and 6 rest on. `git commit --amend`, `rebase`, and `git clean` threaten the same things (linear history, tag anchoring, untracked in-progress work) yet are not named — and an allow pattern for `git commit` silently admits `--amend`. The prompt's own doctrine is to name each item "rather than leaving 'destructive' to interpretation". Direction: add history-rewriting and untracked-file-deleting git to the ask enumeration, or state the principle as the classifier the baseline proposal must apply.
