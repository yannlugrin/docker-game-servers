## 2. Findings

**1. Important — asset templates (7 of 9); rule 1, rule 3.** Every template carrying governance placeholders points to "the glossary in `handoff.md`" (`orient.md:24`, `resume-step.md:28`, `handover-step.md:30`, `approve-step.md:29`, `step-reviewer.md:11`, `state-reviewer.md:20`, `optimize-memory.md:19`). No `handoff.md` exists anywhere in the repository — not in `assets/`, not in `handoff/`. A cold implementer instructed to consult it either fails or goes searching `.claude/spec-work/`, which rule 1 forbids beyond the prompt and `assets/` — the exact excursion the lens flags. The information itself is not missing (PROMPT.md rule 3 defines the governance set inline; each template defines its other placeholders in its own header), so this is a broken pointer, not a broken bootstrap — but it is a dangling reference in the same family the prompt itself polices ("a dangling name is a ritual that silently skips a step"). Direction: repoint the seven references at the bootstrap prompt's rule 3 (or ship the glossary as a file inside `assets/`).

**2. Minor — first task, step-000 baseline vs. rule 9.** Rule 9 declares read-only remote reads free (Steam buildid lookups, public image pulls, `gh`/API reads), yet the step-000 baseline enumeration allows only "the harness, the setup command, the local container lifecycle of rule 9, and the additive and read-only subset of local git". Two reasonable implementations diverge in whether a buildid lookup prompts the operator every time. Softened by the baseline being explicitly proposed for operator review, and by rule 9's guard-hook line for `gh api`; still, the allow set as enumerated is narrower than the free tier as enumerated. Direction: add the free remote-read class to the allow enumeration, or state that its allowance is left to the baseline review.

**3. Minor — rule 1, always-come-back list.** The rule gives (d) its place on the always-come-back list "because it decides whether `ADMIN_PASSWORD` is offered at all, a documented-surface change" — but that rationale applies verbatim to open item (f), whose unfavorable branch adds a documented image-behavior variable (probe-mode selector, PZ §2 item f / root §5.3), and (f) is not on the list. The general rule ("any resolution that changes a requirement, a tier, a documented limitation or the ship decision comes back") would catch (f)'s unfavorable branch anyway, so the rules compose — but the stated reason for the list's membership undercuts the list's own boundary, and an implementer weighing (f) gets contradictory signals about whether a favorable resolution of a surface-deciding item is autonomous. Direction: either add (f), or restate (d)'s reason with what actually distinguishes it (credential semantics / first-boot fatality), so the list's criterion survives contact with the other items.

**4. Minor — rule 3 governance-set resolution vs. the steamcmd track.** The prompt resolves `{{SPEC}}` as "the track's specification with root §3 and §5 standing". For the steamcmd track, the track's specification is a six-line pointer stub; the builder's actual content is root §4 resting on root §2 — neither of which the resolution names as standing. An instantiated `step-reviewer` told to "read those spec sections in `{{SPEC}}`" for a `step-sc-*` step finds nothing in the named file and must improvise through the stub's pointer. Recoverable (the stub redirects, plan steps cite `root §4` explicitly), but the resolution sentence is the one place the prompt defines this and it doesn't account for its own stub. Direction: one clause stating that for the steamcmd track `{{SPEC}}` resolves through the stub to root §4 (and the §2 facts it rests on).

Checked and clean: check families match the stack (Dockerfiles, shell, Actions/compose YAML, markdown, `settings.json`, skill/agent frontmatter, pinned static tools); the external-prerequisites list is complete against what the specs imply and invents nothing false (Actions settings confirmation is extra-spec but real); the rule 9 boundary covers every paid/destructive/shared-state action the spec implies (pushes, any registry publish incl. dev tags, all GitHub/GHCR writes, blanket prune, history-rewriting git), with the local lifecycle and anonymous Steam downloads correctly free; all spec citations in the prompt say what the prompt claims (verified individually, including `.claude/settings.json`'s committed `autoMemoryEnabled: false`, the MIT LICENSE, the remote name, PZ §4's SQLite client, and root §5.5's clients being tiered as a recommended default); template adoption guidance (dangling-name rule, narrower-enumeration rule, assets-deletion lifecycle, `approve-step`'s fallback ladder, `.claude/reviews/` gitignore assumption) is mutually consistent with the prompt's rules 2, 3 and 6.
